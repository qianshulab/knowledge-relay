# 知流架构边界

## 当前产品边界

当前版本仍是个人单用户版：一个所有者、一套本地数据、一个 Nanobot 整理 Runtime，以及一个无工具的检索 Runtime。账号注册、多租户计费和公共开放 API 暂不进入个人版界面。

代码内部不再把“微信消息”视为业务模型。微信 iLink 只是第一个接入适配器，所有通道先转换为统一的 `CaptureInput`，再进入同一条持久化、AI 整理、索引和同步流水线。

```text
微信 iLink ─┐
未来 API  ──┼─> CaptureInput ─> IngestionService ─> 原文持久化 ─> Nanobot 整理
未来 RSS  ──┤                                      ├─> 本地检索索引
未来邮件  ──┘                                      └─> Obsidian 修订同步
```

接入通道 `source.channel` 表示内容如何进入知流，例如 `wechat`、`api`、`rss`、`email`；内容来源 `source.type` 表示内容本身是什么，例如 `wechat_article`、`web`、`paper`、`cti`。两者分开后，从 API 提交的微信公众号文章仍能被正确识别为公众号内容。

## 为什么现在不恢复注册

多用户不是在现有表上加一个注册按钮。只要允许原版 Skill 执行脚本，安全边界就必须覆盖数据库、附件、模型凭据、Workspace、进程和网络。个人版先保持简单，但所有核心记录已经保留所有者和来源边界，接入层也不再直接负责 AI 与同步，后续可以替换租户上下文，而不需要重写消息处理主流程。

## 多用户版的隔离模型

未来托管版建议采用以下边界：

| 资源 | 推荐隔离方式 |
|---|---|
| 业务数据 | PostgreSQL 全表 `tenant_id` + Row Level Security，或高安全租户独立数据库 |
| 原始附件与派生附件 | 每租户独立对象存储前缀、独立短期签名与配额 |
| 模型密钥 | 每租户信封加密，密钥只在其任务执行期间注入 Runtime |
| Nanobot Workspace / Skills | 每租户独立只读基础层 + 可写 Workspace volume |
| 执行型 Nanobot | 每租户独立进程或容器；不能只靠 `session_id` 隔离 |
| 任务调度 | 持久队列按租户限流、重试、死信和幂等处理 |
| 检索 | 默认只检索当前租户索引；工具关闭，运行时可按风险选择共享池或独立实例 |

不建议“每注册一个用户就永久运行一个 Nanobot”。更合理的是为有活动任务的租户按需启动隔离 Worker，并保温一段时间；空闲后回收。这样保留安全边界，也不会让大量不活跃用户长期占用内存。

## 未来开放 API

API 适配器只负责认证、限流、上传校验和转换 `CaptureInput`，不能绕过 `IngestionService` 直接写消息表或调用 Nanobot。建议的第一版契约：

- 使用独立的 `capture:write` 令牌，不复用管理会话或 Obsidian 同步令牌；
- 支持 JSON URL/文本提交与受限 multipart 附件上传；
- 要求 `Idempotency-Key`，相同来源和外部 ID 只能生成一次捕获；
- 原文落库成功后返回 `202 Accepted`，AI 整理异步完成；
- 对 URL、附件大小、MIME、文件名、重定向和私网地址进行校验；
- API、RSS、邮件与微信共用同一套修订发布和 Obsidian 同步协议。

## 演进顺序

1. 完成个人版的统一捕获模型、同步协议和插件体验。
2. 增加个人版 API Token 与 API 接入适配器，但仍只有一个所有者。
3. 把固定所有者上下文替换为 `TenantContext`，数据迁移到 PostgreSQL/对象存储。
4. 引入任务队列与按租户 Nanobot Runtime 调度器。
5. 最后开放注册、配额、审计、计费和管理员能力。

这个顺序能让个人版直接复用未来的大部分业务代码，同时避免为了尚未上线的多租户功能提前承担复杂的运维和安全成本。
