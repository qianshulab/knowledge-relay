# 知流架构

## 产品边界

知流是一个多用户、自托管的智能资源库。微信 iLink、开放 API 以及后续接入的 RSS、邮件或浏览器扩展都只是捕获适配器；链接、文字和附件统一转换为 `CaptureInput`，再进入同一条持久化、整理、索引和输出流水线。

```text
微信 iLink ─┐
开放 API  ──┼─> CaptureInput ─> 原文与附件持久化 ─> Nanobot 整理 ─> 本地检索索引
RSS / 邮件 ─┘                               │                 ├─> 站内知识库
                                            └─> 任务恢复       └─> 可选 Obsidian 同步
```

接入通道 `source.channel` 表示内容如何进入知流，例如 `wechat`、`api`、`rss`、`email`；内容来源 `source.type` 表示内容本身是什么，例如 `wechat_article`、`web`、`paper`、`document`。二者分开后，从 API 提交的公众号文章仍会选择正确的解析 Skill。

## 多用户隔离

每个请求先由登录会话、API 收件令牌或 Obsidian 同步令牌解析出固定 `tenant_id`，随后创建不可变的租户数据库视图。业务方法不接受浏览器提交的租户 ID，也不允许客户端自行切换数据域。

| 资源 | 当前隔离方式 |
|---|---|
| 用户与会话 | 唯一用户名、独立密码哈希、独立登录会话；注册只接受管理员生成的一次性邀请 |
| 消息、附件、索引与配置 | 所有读写固定带服务端解析出的 `tenant_id` |
| 微信连接 | 一个 Bot 只能属于一个租户；扫码会话与确认结果绑定发起用户 |
| API 收件 | 每用户独立、可撤销的哈希令牌；不复用登录或同步令牌 |
| Obsidian | 每个连接绑定一个租户和游标，附件下载按令牌反查所有权 |
| Nanobot | 每个活跃租户独立进程、Workspace、sessions 与 artifacts；只共享管理员维护的模型配置和只读 Skill 基础层 |
| 管理能力 | 模型提供者、执行型 Skills、成员邀请和插件发布仅管理员可操作 |

Nanobot Runtime 按需启动，而不是为每个注册用户永久占用进程。空闲实例自动退出，用户 Workspace 保留；后续任务会在同一隔离目录重新启动。`NANOBOT_MAX_TENANT_RUNTIMES` 控制同时驻留数量，`NANOBOT_TENANT_IDLE_MS` 控制空闲回收时间。

当前 SQLite 适合单机或单节点自托管。需要多节点横向扩展时，应先迁移到支持事务租约和行级安全的数据库，并将附件迁移到按租户前缀隔离的对象存储；不能让多个应用实例直接并发写同一 SQLite 文件。

## 智能整理与网页解析

知流进程不直连模型供应商，也不执行下载的 Skill 脚本。它把受限整理任务交给该用户的官方 Nanobot Runtime：

1. 微信公众号优先调用固定版本的 `wechat-article-extractor`；没有得到有效标题和正文时，再调用 `fetch-skill`。
2. 普通网页由 `fetch-skill` 按其完整回退链读取并转换 Markdown。
3. 链接任务遇到网络波动、限流、上游 5xx、超时或空产物时自动重试；每次尝试和状态均写入数据库。
4. 多次失败后保存原始链接和附件，不阻塞后续收件；用户可以在详情页手动重新整理。
5. 明确的 Mermaid、Canvas 或 Excalidraw 请求由对应的固定版本可视化 Skill 处理；普通收件不自动生成图形文件。
6. 派生 Markdown、`.canvas` 与 `.excalidraw` 只能从该用户 artifact 目录读取；路径、格式、规模与节点引用通过校验后才进入附件和同步，越界或无效产物会被忽略。

“检查连接”只验证基础 Runtime 与模型调用，不代替一次包含网页、工具和外部网络的完整整理任务。真实处理状态以消息记录的排队、处理中、已整理或原文保留为准。

## 收件台、知识库与检索

内容只有“活跃”和“已归档”两类生命周期状态：活跃内容同时服务于收件台和知识库视图，归档可恢复；永久删除会在租户事务中清除消息、AI 结果、图解与附件。知识库不是另一份数据，而是对已整理内容的阅读与聚合视图。内容形态使用稳定枚举，领域、知识点、工具、摘要与要点由 AI 整理后进入本地索引，并随新内容动态变化。

全库知识关系概览只读取已经持久化的索引，不在每次打开时随机生成。单条内容的智能图解采用按需生成与版本缓存：用户首次查看时才由 Nanobot 选择合适图形并产生结构，服务端将结果绑定到消息修订；再次打开直接复用，内容重新整理后缓存失效，显式重新生成才再次调用模型。

服务启动时会扫描所有未停用租户的 `pending` 与 `processing` 记录。恢复范围不依赖微信连接，因此仅通过 API 收件的用户也能继续未完成任务；单次分批读取，直到该租户没有遗留任务。

自然语言检索采用两阶段链路：无工具的 Nanobot 检索 Runtime 把问题转换为受限检索计划，知流再在当前租户的本地索引中匹配。模型不可用时直接降级为本地关键词检索。检索入口不提供通用对话、命令执行或数据写入能力。

## API 收件

`POST /api/captures` 使用独立 Bearer Token，支持 URL 或文本，并通过 `externalId` 实现来源内幂等。API 适配器只负责认证、输入校验和转换 `CaptureInput`，不能绕过 `IngestionService` 直接调用模型或写业务表。原文持久化后返回 `202 Accepted`，整理异步完成。

附件上传、RSS 和邮件可以继续按照同一模式增加适配器；不需要修改整理、检索、资源状态和 Obsidian 同步协议。

## Obsidian 是可选输出

站内知识库不依赖 Obsidian。需要本地 Markdown 工作流的用户可以创建一个或多个同步连接；不需要 Obsidian 的用户仍可完成捕获、解析、动态主题浏览、检索、完整文章阅读、附件预览和按需智能图解。

同步服务只发布已经完成整理或明确降级的稳定修订。插件按连接令牌拉取、校验附件、幂等写入并确认批次；确认后只推进该连接的游标，不改变其他用户或其他连接的状态。
